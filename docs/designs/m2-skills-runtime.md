# Design: AEGIS M2 — Claude Skills Runtime (Minimal Wedge)

## Problem Statement
AEGIS has no mechanism to give the agent a reusable, declarative "how to approach this task" layer. Today `backend/app/agent.py` hardcodes two tools (`calculator`, `search_workspace`) directly in a Python list and a dispatch function. Any new repeatable capability requires editing `agent.py` by hand — there is no separation between "what the agent can do" and "how it should approach a specific recurring task," and no way to load Claude-compatible `SKILL.md` files that already exist in the wild.

## Demand Evidence
Pre-product, solo learning project — no external users yet. The demand evidence is internal: the gap is total (confirmed directly against the M1 codebase — `agent.py`, `tools.py` — nothing resembling skill discovery/loading exists), and the user confirmed it directly: "Nothing exists yet — it's pure gap."

## Status Quo
Any new capability today means hand-editing `TOOLS` and `_run_tool` in `agent.py`. There is no file-based, declarative way to add instructions or scope tool access per task — every addition is a code change to the core agent loop.

## Target User & Narrowest Wedge
Target "user" at this stage is the builder themself (COGMUNK founder), learning by building. Narrowest wedge, confirmed directly: "Discover → parse → load → execute ONE skill end-to-end." Selection logic can be trivial (keyword match) at this size — the point is proving the full mechanism, not sophisticated relevance ranking.

## Constraints
- Must reuse M1's architecture and conventions; must not modify M1 behavior when no skill is selected.
- No unnecessary dependencies; no generic agent framework.
- Must parse Claude-compatible `SKILL.md` (YAML frontmatter + Markdown body) — not a custom config format — so skills written elsewhere (including Anthropic's own) are usable.
- Explicit instruction: prioritize hands-on learning over production hardening. Architecture should be *extensible* toward commercial use later, but must not add production complexity (sandboxing, marketplace trust, multi-tenant isolation) prematurely.
- Security boundary for M2: local, developer-authored skills only — not a third-party skill marketplace.

## Premises
1. The gap is real and total: no existing separation between "what the agent can do" and "how to approach a recurring task." — **Agreed.**
2. The full 8-deliverable M2 scope is good direction but larger than the narrowest wedge already chosen; several items (rich selection, broad permission tooling, full lifecycle tracing) are valuable but don't have to ship before the proof-of-concept works. — **Agreed.**
3. Skill selection should follow Anthropic's own documented progressive-disclosure pattern (metadata-only match at discovery; full `SKILL.md` body loaded only once selected) rather than invent a new mechanism. — **Agreed.**
4. Given the "don't add production complexity prematurely" constraint, the M2 security boundary assumes local, developer-authored skills; cryptographic provenance/signing, sandboxed execution, and marketplace trust scoring are explicitly out of scope. — **Agreed.**

## Landscape Findings
Web search (no Aside on this Linux host, used WebSearch tool directly) confirmed:
- Anthropic's own Claude Skills architecture uses exactly the 3-level progressive disclosure this design adopts: Level 1 (name+description metadata, always visible to the selector), Level 2 (full `SKILL.md` body, loaded only on selection), Level 3 (bundled scripts/reference files, loaded or executed only on demand). Source: Claude Platform Docs / Anthropic engineering writeups on Agent Skills.
- Independent security literature on agent tool/instruction loading agrees on two points relevant here: (a) instructions pulled in from skill files are a real security surface and need gating/provenance awareness, not blind execution; (b) permission enforcement should happen outside the model (e.g., intersecting allowed-tool lists before the API call), not rely on the model "choosing" to respect a boundary.
- **No eureka / no contrarian finding.** The conventional wisdom (progressive disclosure + external enforcement) is sound and directly matches what AEGIS needs to build — we build on it rather than challenge it.

## Approaches Considered
### Approach A: Minimal viable — single-skill proof of loop (REVISED — see Revision Note)
Discover skills under a `backend/skills/` directory, parse each one's YAML frontmatter (`name`, `description`, optional `allowed-tools`) + Markdown body. **Selection is model-driven, not an external keyword matcher**: every discovered valid skill's `name` + `description` (Level 1 metadata only — never the body) is injected into the system prompt as an "Available skills" list on every request, and the model is given one new tool, `load_skill(name)`, to fetch a specific skill's full body (Level 2) when it decides that skill is relevant. This mirrors the real Claude Skills mechanism exactly: Claude itself judges relevance from the description text, never an external program doing word matching.

> **Revision note (CEO review, Outside Voice finding):** The original Approach A used an external whole-word keyword matcher against a `triggers` field. An independent review verified against a real `SKILL.md` on disk (bundled with this repo's own `fastapi` dependency) that real Claude-compatible frontmatter has no `triggers` field — only `name`/`description`, with selection done by the model reading descriptions in context. The keyword-matcher design was not a simplified version of the real mechanism; it was a different, incompatible one, and would have failed to select any real third-party skill. This revision replaces it with model-driven selection, which is both more compatible AND simpler: no whole-word-vs-substring matching, no discovery-order tie-break, no `NO_MATCH`/`MATCHED` taxonomy — selection reduces to "did the model call `load_skill`."

When `load_skill(name)` is called: the backend looks up that name among the request's successfully-discovered skills, returns its full body as the tool result (which the model then follows as instructions for the rest of the conversation), and scopes the Claude call's `tools` list for subsequent rounds in this request to the intersection of M1's existing `TOOLS` and the skill's declared `allowed-tools`. If `name` doesn't match any valid discovered skill (the model hallucinated a name), the tool result is an error and no scoping change occurs. At most one skill may be loaded per request (M2 scope — a second `load_skill` call in the same request is rejected with an error result; multi-skill composition stays deferred in `TODOS.md`, now for an additional reason: nothing in this design prevents it, it's deferred by policy, not by mechanism). `load_skill` is only offered as a tool when at least one skill was successfully discovered — with zero valid skills, the tool list and system prompt are identical to plain M1 behavior.

**Enforcement scope note (0I, CEO review, still holds; sharpened at /review):** pre-call list filtering is the *sole* enforcement point for M2 — there is no `_run_tool`-level defense-in-depth check for the base tools (`calculator`/`search_workspace`). This is sufficient because M2 is single-request, single-skill-load scope: skill state is rebuilt fresh on every `/api/chat` call, with no reference to the client-supplied `history`. Note this means a loaded skill's restriction does not persist to the *next* `/api/chat` call of the same conversation either — not only "can't switch between two different skills across turns," the restriction resets completely every call. Revisit if multi-turn persistence of a skill's restriction becomes real (tracked in `TODOS.md`).

Discovery and parsing happen fresh on every request (no startup-time caching — consistent with M1's stateless, per-request `ask_aegis` call). **Tool-allowlist enforcement after a skill loads is pre-call list filtering only**: once `load_skill` returns, the next round's `tools` list sent to the Claude API is already the intersection of `TOOLS` and the loaded skill's `allowed-tools` — the model is never offered a tool outside that list, so there is no post-call "the model requested a denied tool" case. `TOOL_DENIED` below describes what got filtered out before the call, not a runtime rejection.

Trace stages via the existing `write_trace`, using these event names and reason codes:
- `skill_discovered` — one event per skill file found during that request's discovery pass, with `reason` one of `OK`, `PARSE_ERROR` (malformed or missing frontmatter, or a file that fails to decode as UTF-8 — the skill is excluded from the metadata list for this request and the error is surfaced, per Success Criteria's "fail loudly"), or `UNKNOWN_TOOL_DECLARED` (the skill's `allowed-tools` names a tool not present in M1's `TOOLS` registry — also excluded and surfaced).
- `skill_loaded` — one event per `load_skill` tool call, with `reason` one of `LOADED` (name matched a valid discovered skill; body returned), `LOAD_ERROR` (name didn't match any valid discovered skill), or `ALREADY_LOADED` (a second `load_skill` call in the same request — rejected, M2's single-skill-per-request cap).
- `skill_tool_scoping` — one event the round after a skill is successfully loaded, with `reason` one of `TOOL_DENIED` (the loaded skill's `allowed-tools` excluded one or more tools from M1's base `TOOLS` list, which were filtered out before the next call) or `TOOL_ALLOWED` (no filtering was needed). The `allowed-tools` field has two distinct states: **omitted entirely** means the skill inherits full access to M1's base `TOOLS` list (always `TOOL_ALLOWED`); **present as an empty list** (`allowed-tools: []`) means deny-all — every base tool is filtered out and `TOOL_DENIED` fires for each one.

Effort S (human ~1 day / CC ~45 min) — **recalibrated to S/M** (human ~1-1.5 days / CC ~60 min) per the outside-voice effort-calibration finding: the accepted scope (4 cherry-picks plus this revision) adds up to more than the original single-skill-match estimate, even though each addition was individually rated S. Risk Low. Reuses M1's `TOOLS`/`_run_tool` dispatch, `write_trace`, `Settings` pattern.

### Approach B: Ideal architecture — registry + permission-aware selector
A `SkillRegistry` indexing every skill's metadata (never bodies) at startup, a scored selector, lazy body loading on selection, explicit allowlist-intersection enforcement, per-stage tracing, and a broader test matrix (malformed frontmatter, unknown declared tools rejected rather than silently ignored). Effort M (human ~3-4 days / CC ~3-4 hrs), risk Medium. This is effectively roadmap milestone 3 ("tool registry, bounded loops, permissions, traces, verification") pulled forward.

### Approach C: Config-only skill profiles (rejected)
Skip SKILL.md parsing; model skills as plain YAML/JSON. Simpler parser, but breaks the explicit "Claude-compatible SKILL.md" requirement and doesn't transfer to real Claude Skills usage. Rejected on first pass — named only for completeness.

## Recommended Approach
**Approach A.** It matches the user's own stated priorities exactly — prove the end-to-end mechanism hands-on this week, avoid premature production complexity — while remaining a strict subset of Approach B: nothing in A needs to be thrown away to grow into B later (same file format, same trace events, same tool-scoping idea, just less of each). The CEO/scope review that follows this design doc will size the exact file/module boundaries, test matrix, and acceptance criteria for implementation.

## Open Questions
Tracked in `TODOS.md` (created alongside this revision, updated at ROW-10):
- Multi-skill composition (more than one skill loaded within a single request) — deferred by policy, not mechanism: `load_skill` rejects a second call per request (`ALREADY_LOADED`) even though nothing about model-driven selection prevents it technically.
- Where skill-declared tool permissions intersect with a future multi-tenant/user permission model — deferred until there is more than one user.
- Level 3 (bundled scripts/reference files that a skill's body links to, e.g. `references/*.md`) is NOT implemented — only Levels 1-2 (metadata always visible, body loaded via `load_skill`). A real skill whose body references bundled files will have those links go nowhere once injected as plain text. Named explicitly here per the outside-voice completeness finding (previously an undocumented silent gap).

## CEO Review — Accepted Scope Additions (2026-11-12, Selective Expansion)
The CEO/scope review that followed this design doc accepted four additions beyond the bare minimal wedge, each approved individually (rationale for #2 updated at ROW-10 below):
1. **`pyyaml` dependency** for frontmatter parsing — real Claude-compatible SKILL.md frontmatter is YAML (quoted strings, list values); a hand-rolled parser risks silent misparse.
2. **Second demo skill fixture** — now proves the model can distinguish between two skills by description alone and that `ALREADY_LOADED` correctly rejects a second `load_skill` call in one request (updated from the original "discovery collision" rationale, which no longer applies — there's no keyword collision to test once selection is model-driven).
3. **`GET /api/skills` read-only introspection endpoint** — lists discovered skills (name, description, allowed-tools) without grepping `traces.jsonl`.
4. **Structured trace reason codes** distinguishing a skill being loaded vs a tool being denied vs normal execution — without this, these cases are indistinguishable in the trace log, which defeats the point of tracing permission enforcement specifically.

Nothing else was added; all three cherry-pick candidates offered were accepted, none deferred or cut.

## Success Criteria
- A skill under `backend/skills/<name>/SKILL.md` is discovered, its frontmatter and body parsed without errors.
- Every discovered valid skill's `name` + `description` (not its body) appears in the system prompt on every request, and `load_skill` is offered as a tool whenever at least one valid skill exists.
- Calling `load_skill(name)` with a name matching a valid discovered skill returns that skill's full body as the tool result; calling it with a non-matching name returns an error (`LOAD_ERROR`) and changes nothing about tool scoping.
- The loaded skill's declared `allowed-tools` (if any) are enforced on the next round's Claude call — a tool not in that list is not offered to the model, verified by a test, not just by convention.
- A second `load_skill` call in the same request is rejected (`ALREADY_LOADED`) — M2's single-skill-per-request cap.
- Every stage (discovery, load, tool-scoping decision) appears in `backend/.traces/traces.jsonl` as a distinct event (`skill_discovered`, `skill_loaded`, `skill_tool_scoping`) with the reason codes defined in Approach A above.
- A second skill fixture coexists with the first; given a query whose intent clearly matches one skill's description over the other, the model loads the correct one (an integration-level behavioral test, not a deterministic unit assertion, since selection is now the model's judgment call — see Section 6 test-review update).
- `GET /api/skills` returns the discovered skills' metadata (name, description, allowed-tools) without exposing instruction bodies. On a discovery error, it returns an empty list (200) with the cause logged to `traces.jsonl` — the same graceful degradation as the chat path, not a 500 (CEO review, Section 2).
- M1's existing behavior (no skill directory, or the model never calls `load_skill`) is unchanged — existing M1 tests still pass unmodified.
- Malformed/missing frontmatter and a skill declaring an unknown tool both fail loudly (logged + surfaced), never silently ignored.

## Distribution Plan
Existing deployment pipeline covers this — AEGIS is a local FastAPI service; skills ship as files in the repo (`backend/skills/`), no separate packaging or release process needed at this stage.

## Dependencies
- Builds directly on M1's `agent.py`, `tools.py`, `tracing.py`, and `config.py`.
- New dependency: `pyyaml` (approved by CEO review, above) for Claude-compatible frontmatter parsing — `yaml.safe_load` only, never `yaml.load`/`yaml.unsafe_load` (hard requirement, CEO review Section 3).
- New `Settings` field `skills_dir` (default `"skills"`), mirroring `workspace_dir`'s existing pattern (CEO review Section 5) — not hardcoded.
- Depends on M1 remaining unmodified in behavior for the no-skill-matched case.

## Implementation Notes (0I, Temporal Interrogation)
- `backend/skills/` must not overlap the paths `search_workspace` scans under `workspace_dir` — skill bodies are instructions injected into the system prompt, not searchable workspace content.
- Existing agent tests (`test_agent.py`) mock the Anthropic client but never assert on the `tools=` kwarg passed to `messages.create` — new tests need that assertion to verify allowlist scoping actually happened, not just that no error was raised.
- Write down the skill-authoring contract (required vs. optional frontmatter fields) somewhere persistent — e.g. a short `backend/skills/README.md` — so the format doesn't live only in the Assignment's throwaway parse script. **Required, not optional** (CEO review Section 10): without it, this is the one gap that would make the mechanism non-obvious to a new engineer in 12 months.

## The Assignment

This forces contact with the actual file format's edge cases (frontmatter delimiters, required vs. optional fields) before any architecture gets built around assumptions about it.
