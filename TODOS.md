## From M2 (Claude Skills Runtime) — deferred 2026-11-12 (updated after ROW-10 revision)

- **Multi-skill composition.** M2 loads at most one skill per request (`load_skill`'s second call in a request is rejected, `ALREADY_LOADED`). Running more than one skill's instructions together is deferred by policy, not by mechanism — nothing about model-driven selection prevents it technically, it's just not exercised or tested in M2. Source: `docs/designs/m2-skills-runtime.md`.
- **Multi-tenant / multi-user permission model.** Skill-declared `allowed-tools` are enforced per-request today; how that interacts with per-user permissions is deferred until AEGIS has more than one user. Source: `docs/designs/m2-skills-runtime.md`.
- **`_run_tool`-level allowlist enforcement (defense-in-depth).** M2 enforces the loaded skill's `allowed-tools` only by pre-filtering the `tools=` list sent to the Claude API; there's no second check inside `_run_tool` itself. Revisit if multi-turn skill-switching (a conversation `history` spanning more than one skill's tool scope) becomes a real case. Source: `docs/designs/m2-skills-runtime.md`.
- **Tool-scoping restriction does not persist across `/api/chat` calls of the same conversation (sharper than it sounds).** `ask_aegis()` rebuilds its skill state fresh on every call with no reference to the client-supplied `history`. This is not just "can't switch between two skills across turns" — if turn 1 loads a skill with `allowed-tools: []` (deny-all) and the client resends that turn in `history` for turn 2 (ordinary multi-turn chat), turn 2 starts with the full, unrestricted tool set again; nothing re-establishes the prior restriction. Found by the /review adversarial pass (2026-11-12), deliberately deferred rather than fixed, because M2's own design doc already scopes enforcement to "single-request, single-skill-load" and reconstructing loaded-skill state from `history` is a real architecture change, not a one-line fix. Revisit when multi-turn conversations that load a restrictive skill become an actual use case — at that point, reconstructing `loaded` state from `history`'s prior `load_skill` tool_result is the likely fix. Source: `docs/designs/m2-skills-runtime.md`, backend/app/agent.py `ask_aegis()`.
- **Level 3 progressive disclosure (bundled scripts/reference files).** Real Claude Skills can bundle files a skill's body links to (e.g. `references/*.md`), loaded or executed only on demand. M2 implements only Levels 1-2 (metadata always visible, body loaded via `load_skill`) — a real third-party skill whose body references bundled files will have those links go nowhere once injected as plain text, with no failure mode or trace event covering it. Found by the outside-voice review as a silently-dropped (not deferred) gap; now explicitly tracked. Revisit once a real skill actually needs bundled files. Source: `docs/designs/m2-skills-runtime.md`.
