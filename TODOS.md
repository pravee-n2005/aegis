## From M2 (Claude Skills Runtime) — deferred 2026-11-12 (updated after ROW-10 revision)

- **Multi-skill composition.** M2 loads at most one skill per request (`load_skill`'s second call in a request is rejected, `ALREADY_LOADED`). Running more than one skill's instructions together is deferred by policy, not by mechanism — nothing about model-driven selection prevents it technically, it's just not exercised or tested in M2. Source: `docs/designs/m2-skills-runtime.md`.
- **Multi-tenant / multi-user permission model.** Skill-declared `allowed-tools` are enforced per-request today; how that interacts with per-user permissions is deferred until AEGIS has more than one user. Source: `docs/designs/m2-skills-runtime.md`.
- **`_run_tool`-level allowlist enforcement (defense-in-depth).** M2 enforces the loaded skill's `allowed-tools` only by pre-filtering the `tools=` list sent to the Claude API; there's no second check inside `_run_tool` itself. Revisit if multi-turn skill-switching (a conversation `history` spanning more than one skill's tool scope) becomes a real case. Source: `docs/designs/m2-skills-runtime.md`.
- **Tool-scoping restriction does not persist across `/api/chat` calls of the same conversation (sharper than it sounds).** `ask_aegis()` rebuilds its skill state fresh on every call with no reference to the client-supplied `history`. This is not just "can't switch between two skills across turns" — if turn 1 loads a skill with `allowed-tools: []` (deny-all) and the client resends that turn in `history` for turn 2 (ordinary multi-turn chat), turn 2 starts with the full, unrestricted tool set again; nothing re-establishes the prior restriction. Found by the /review adversarial pass (2026-11-12), deliberately deferred rather than fixed, because M2's own design doc already scopes enforcement to "single-request, single-skill-load" and reconstructing loaded-skill state from `history` is a real architecture change, not a one-line fix. Revisit when multi-turn conversations that load a restrictive skill become an actual use case — at that point, reconstructing `loaded` state from `history`'s prior `load_skill` tool_result is the likely fix. Source: `docs/designs/m2-skills-runtime.md`, backend/app/agent.py `ask_aegis()`.
- **Level 3 progressive disclosure (bundled scripts/reference files).** Real Claude Skills can bundle files a skill's body links to (e.g. `references/*.md`), loaded or executed only on demand. M2 implements only Levels 1-2 (metadata always visible, body loaded via `load_skill`) — a real third-party skill whose body references bundled files will have those links go nowhere once injected as plain text, with no failure mode or trace event covering it. Found by the outside-voice review as a silently-dropped (not deferred) gap; now explicitly tracked. Revisit once a real skill actually needs bundled files. Source: `docs/designs/m2-skills-runtime.md`.

## From M3 (Context Engineering & Persistent Memory) — deferred 2026-11-13 (HOLD SCOPE)

- **Cross-session / global memory.** M3 scopes `memories` rows to a single `session_id` — satisfies "persistent memory extraction and retrieval" at session scope. True cross-session or cross-account memory needs a user/account concept that doesn't exist yet (Roadmap Milestone 7, authentication/tenancy). Source: `docs/designs/m3-context-memory.md`.
- **LLM-based memory extraction.** M3's `extract_memories` is a deterministic heuristic (regex over explicit statements like "remember that..."), not an LLM call — required by the "do not make unnecessary live LLM calls" constraint. Higher-recall LLM-based extraction is a real future upgrade once that constraint is relaxed or extraction quality becomes a measured problem. Source: `docs/designs/m3-context-memory.md`, `backend/app/memory.py`.
- **Embedding/relevance-ranked history and memory selection.** M3 selects context by recency + token budget, not semantic relevance — required by the constraint to avoid vector databases unless technically justified; recency is sufficient at this scale. Revisit if session length or memory count grows enough that recency stops being a good proxy for relevance. Source: `docs/designs/m3-context-memory.md`, `backend/app/context.py`.
- **Retention/eviction policy for unbounded session growth.** Nothing in M3 caps how large a session's `messages`/`memories` tables can grow over time; no stated requirement for storage limits yet, but this is a real gap, not a hidden one. Revisit when disk usage or per-request query cost on a very old session becomes a measured problem. Source: `docs/designs/m3-context-memory.md`.
- **Pagination on `GET /api/sessions/{id}/messages`.** Returns the full message list for a session with no limit/offset; fine at this scale, a real gap once a session accumulates thousands of turns. Source: `docs/designs/m3-context-memory.md`, `backend/app/main.py`.

## From M4 (RAG & Document Intelligence) — deferred 2026-11-15 (HOLD SCOPE, plan stage)

- **OpenRouter provider migration.** No evidence it's needed for M4; the chat integration stays on the Anthropic SDK (`anthropic` package) as verified during architecture recon — no OpenRouter code, env var, or dependency exists anywhere in this repo. Revisit only if a provider switch is explicitly requested as its own scoped milestone. Source: `docs/designs/m4-rag-document-intelligence.md`.
- **Hosted/API-based embeddings.** M4 uses a local `sentence-transformers` model per explicit user preference; `embeddings.py`'s interface is designed so swapping to a hosted provider later is a contained change behind that interface, not a rewrite. Revisit if the ~90MB `torch`/`sentence-transformers` dependency weight becomes a real deployment constraint. Source: `docs/designs/m4-rag-document-intelligence.md`.
- **`sqlite-vec` or any native vector-search extension.** M4 uses brute-force cosine similarity in Python over a plain SQLite table, assumed adequate up to ~5,000 chunks/session; the `retrieval` trace event logs `chunk_count` per query so this ceiling is checked against real usage. Revisit only once that's a measured performance problem. Source: `docs/designs/m4-rag-document-intelligence.md`.
- **OCR for scanned PDFs.** M4 treats a PDF with no extractable text as a defined `status="empty"` case, not an error — it is not OCR'd. Revisit if scanned-PDF support becomes a real requirement. Source: `docs/designs/m4-rag-document-intelligence.md`.
- **Retrieval evaluation harness.** Roadmap Milestone 2 names "retrieval evaluation" as part of the RAG milestone; M4 does not build one. A future milestone once retrieval quality needs measurement beyond manual spot-checking. Source: `docs/ROADMAP.md:2`, `docs/designs/m4-rag-document-intelligence.md`.
- **Cross-session document reuse.** M4 scopes documents to a single `session_id` (same pattern as M3's memories), per the user's explicit constraint ("Enforce strict session isolation for documents and retrieved chunks"). A durable, reusable document library across sessions is a real but different feature — would need its own schema/API design, not an extension of the session-scoped `documents`/`chunks` tables. Source: `docs/designs/m4-rag-document-intelligence.md`.
- **No correlation ID in error response bodies.** Every endpoint across M1-M4 generates a `request_id` and writes it to the internal `traces.jsonl` file (`tracing.py`), but never returns it in the HTTP response body — so a caller (human or agent) that hits a 4xx/5xx has no way to correlate that specific failure with its matching trace line without timestamp-guessing. Found during M4's DX review (Pass 3, agent-ready error contract's "trace" item) while reviewing the new 503 `EmbeddingUnavailableError` path, but it's a cross-cutting gap across every existing endpoint, not specific to M4 — fixing it only for M4's 3 new error paths would create a new inconsistency with M1-M3's identical pattern. Revisit as its own observability pass across `main.py`'s whole error-handling surface. Source: M4 DX review, `backend/app/tracing.py`, `backend/app/main.py`.

## From M4 security hardening pass — deferred 2026-11-15

- **Process-isolated PDF extraction adds `multiprocessing`/`spawn` startup latency to every upload.** `documents._extract_pdf_isolated()` spawns a fresh child process per upload (fork-unsafe otherwise, since `ingest()` already runs inside `asyncio.to_thread`). Fine at this project's scale; revisit with a persistent worker pool if upload latency becomes a measured problem under real concurrent load. Source: `backend/app/documents.py`.
- **`SENSITIVE_TOOLS_AFTER_DOCUMENT_CONTENT` is a hand-maintained set, not derived from any tool metadata.** A future tool that reads sensitive local state must be added to this set explicitly in `agent.py`; nothing enforces that at tool-registration time. Revisit if the tool count grows enough that this becomes error-prone. Source: `backend/app/agent.py`.
- **The gate blocks a sensitive tool for the rest of the turn, not just calls caused by the untrusted content.** A same-round `search_workspace` call the model generated before seeing the document content is blocked too (conservative by design, not a bug) — if this proves too restrictive in practice, revisit scoping the gate to only rounds strictly after the one where `search_documents` was called. Source: `backend/app/agent.py`.
